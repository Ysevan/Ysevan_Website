名片优先，现行做法。

六条

  1. 名片优先。门厅只告诉访客一件事，不放列表、预览、统计和引导按钮（清单见名片为主那条）。
  2. 少即是真。每个元素要么承载内容，要么承载导航。唯一的例外是四处绿植装饰，完全不占布局，不响应事件，不带动画。
  3. 手作气质，工程克制。楷体、行楷和宋体只用在少数标题和数字上，正文一律用黑体。饱和色严格限制用量和位置。
  4. 零固定高度。内容多就往下长，内容少就居中留白。
  5. 不阻塞。开场动画、自托管字体和装饰SVG都不能挡住首屏内容，也不能延迟数据获取。
  6. 两个时辰，一间屋子。夜里不做反相，是同一间屋子的夜晚，冷夜暖灯。切换入口是顶栏的墙壁开关（见交互页墙壁开关）。

为什么

这六条把小屋是一张名片、一间手作的屋子这个定位，拆成了能逐条核对的句子。新需求先按这六条过一遍，违背哪条就不做，或者换一个不违背的做法。

降级后和改动前的页面逐像素相同

3D、漂浮、走进小屋这类增强层降级后，要和改动前的构建逐像素比对，差异必须是0。不留占位，不留半透明的残影，版面不挪动一个像素。

  • 通用
  • 2026-09-20定

示例左边是改动前的页面，中间是加了增强层、在这一档降级后的页面，右边是逐像素比出来的差（红点）。可以换几种降级写法对比。

差异像素0，降级后和改动前的页面完全相同。

验收

在1440×900下和改动前的构建逐像素比对。三页的白天和夜里，各在滚动位置0、没动过鼠标时比一次。减弱动效、800px宽、触摸、省流量、禁用JS、WebGL失败这六档，动过鼠标后再比。差异像素都是0，没有一档挂上画布。首屏多出来的只有那个岛本身（gzip后约1.3KB，一个请求）。

为什么

降级档的访客看不到增强效果，他看到的应该就是没有增强时的那一页。降级后还留下任何东西，都是给他的页面平白多加了东西。逐像素比对是唯一不靠眼睛的判断方法，结果是0才算过。

坑

夜里有一块会明暗起伏的画（8秒一次的夜灯），比之前先把那块画布藏起来。同一个构建和自己比也有差异时，量到的是环境，不能算在增强层上。

行为不取决于用户忘掉的往事，隔离不留痕迹

一个功能的行为，如果取决于用户早就想不起来的历史状态，一律否掉，不用先问。库和库之间的隔离，连能看出另一个库存在的条数、日期和提示都不能出现。

  • 通用
  • 2026-09-23定

示例日程安排生活库的本周回顾（示例数据）。底下那行往事是三个月前做的事，你早就忘了。切换它，看两种设计下回顾页会不会变。

本周回顾生活库，9月21日到9月27日

    往事，三个月前（你早就忘了）

    只看当前库，往事怎么变，回顾页都一样，也看不出另一个库存在过。

    实例

    周回顾原本可以在工作库已解锁时合并显示两个库。但工作库上锁时是加密存储的，密钥只在它自己那个已解锁页面的内存里，生活库页面读不到，所以合并只会在工作库从没设过口令时发生。屋主会看到回顾页有时有工作、有时没有，却不会想到这和当初设没设口令有关。现行做法是周回顾只看当前库，也不出现另一个库上锁了这类提示。

    为什么

    用户解释不了的行为就是bug，即使代码完全按设计运行。控制室的原话是「这条理由比隔离原则本身还硬」。代价是某些天的回顾看起来像普通的空白日，这是隔离本来就要付出的。

    护栏

    只看当前库的三条测试跑整个<App />，走真实的读库键路径，不直接给组件传数组。直接传数组的话，读错键这种错根本不会发生。这三条也先红过一次，让组件临时去读另一个库，三条当场全红。

    数值

    台式：  2040 × 1019  DPR 1.25  Microsoft Basic Render Driver（WARP 软件渲染）  --scale 1.417（未封顶）

    怎么用

    • 大屏两档都要拍。2040那档看没封顶的纯等比，2552那档才看得出1.45封顶后的样子。
    • 为什么没有3D这个问题只出在台式机上，笔记本和手机本来就有3D。
    • 手机按417拍图。判断装不装得下用750（最坏的情况），判断会不会显得空用903。和高度有关的尺寸一律用dvh或svh，不用裸vh。

    为什么

    台式机物理宽2560，Windows缩放125%，视口其实是2040。按2560推出来的两个结论，1.45封顶在他的机器上会触发、填满和等比要取舍，都错了。所以公式必须是视口除以1440。线性爬坡在2040处只给1.241，比等比的1.417小约12.4%（反过来算是等比大14%，plan的SPEC原来写成小14%，比反了，plan提交ab7bbd4已经改正）。

      • 1100（侧栏还在的窄桌面）和768（900以下侧栏收成顶栏，还没到600换成底部标签栏）。

      无头Chrome设视口，不设窗口

      用Emulation.setDeviceMetricsOverride设视口（puppeteer的setViewport内部也是它）。顺序是先navigate再设视口，设完当场读innerWidth、devicePixelRatio和决定版面档的媒体查询，对不上就抛错。

      • 通用
      • 2026-09-23定

      示例四种设法（示意，不开浏览器）。截出来的图都是手机尺寸，里面的版面却不一定按手机排。打开对账断言才分得出来。

      代码

      async function setViewport(c, w, h, dpr, mobile) {
  await c.send("Emulation.setDeviceMetricsOverride",
    { width: w, height: h, deviceScaleFactor: dpr, mobile, screenWidth: w, screenHeight: h });
  const got = await evaluate(c, "({w: innerWidth, dpr: devicePixelRatio})");   // 已经 navigate 过
  if (got.w !== w || Math.abs(got.dpr - dpr) > 1e-6) throw new Error("viewport mismatch");
}

      三个成因

      1. --window-size设的是窗口。macOS的最小窗口宽度把它夹到500，不报错，PNG照样是390×844，布局却按500排，手机断点没有命中。
      2. 页面没有<meta name="viewport">，又开了mobile:true，Chrome给980的默认布局视口。
      3. 在还没navigate的about:blank上读，读到980（读的是上一页）。

      三种现象一模一样，都不报错，只能靠对账断言区分。这道护栏也要真的红过一次，拿掉viewport meta的副本读到980，断言抛错，正常页面读到390，通过。

      坑

      只核尺寸不够，(max-width:900px)、(hover: hover) and (pointer: fine)这几条决定版面档的媒体查询也要核。尺寸都对、跑的却是桌面版面时，截图、帧率和画布尺寸全是错的。

      手机模拟下判溢出，跟目标宽度比

      开了mobile:true时，内容撑破屏幕后，Chrome不让scrollWidth变大，而是把innerWidth本身撑宽，所以scrollWidth === innerWidth永远成立。判据要跟目标宽度比，不跟当时的innerWidth比，并逐个检查元素右缘不超过目标宽度。

        七条

        1. 不许拿可变的显示文案当判定依据。
        2. 测试先让它红一次再修绿。突变要精确，一次只坏一件事。

            判据里不掺自己加的量
            
        
            限帧、节流、去抖都会让量出来的间隔只剩几个离散值，阈值刚好落在其中一个值上时，降不降档就成了随机的。阈值要按这一档承诺的帧率写成倍数，量这一段时间里实际送出去几帧（均值），不在台阶上取中位数。

              实例
              小屋3D看门狗量帧间隔，间隔里掺着自己加的29ms限帧（rAF是60Hz，所以只能是33.3、50、66.7），阈值50恰好落在其中一个台阶上，同一个构建三次量到47.7、49.7、59.6。屋主说的「有时候有3D有时候没有」就是这样来的。
              
        
              做法
              1. 用相对阈值。按这一档自己要求的帧率的比例写，不写绝对毫秒，人为限帧的影响就被除掉了。
              2. 量连续的量。均值就是这一秒实际送出去几帧，不在量化台阶上取中位数。做对之后，处理限了帧的那类分支应当整个消失。
              3. 几个条件同时成立才判定时，至少一个是干净的量，而且它能单独决定结果。更好的问法是这是不是我造成的，而不是现在好不好。
              
        
              坑
              不要改成量画一帧花多久就算完。WebGL是异步的，用performance.now()夹着render()只量到CPU提交的时间（gl.finish() 0.2ms，readPixels 95.6ms，差478倍），照字面改会得到一个只要提交得快就判健康、实际什么也查不出的看门狗。节流器本身不受这条约束，限帧只管送帧的节奏，不拿来做判断。

                • 输入法回车，拦提交只认isComposing，不认229。安卓软键盘不在合成时也常报229，拦了会让键盘上的搜索键按了没反应，后果重。提前return不处理的那一步可以两个都认，后果轻。
                
        
                用在哪
                本站boot.js里，背景模糊设为自动时，star-gpu没测过就先按lite，star.js空闲时测一次再改。
                
        
                诊断法
                阈值反复调不准时，先构造两个方向的反例。刷刷那次证明，同一个判据会放过22帧的卡顿，又把流畅的30Hz屏判成慢。两种情况同时成立，说明只调阈值修不好，必须换判据。

                        文档同一轮改，错话的三种形态
                        
        
                        改了什么，就在同一轮把对应的文档改掉，不留待办。收尾时把这一轮动过的概念关键词在全仓grep一遍。错话有三种，数字过期、正确的指针指向错话、结论还对但理由已经不成立，找法各不相同。
                        
        
                        • 通用

                          三种形态
                          1. 数字过期，最好找。拿旧值当关键词在全仓grep。那次一下找出13处，四个岛的实现和改动点旁的注释都对，漏的全是文件头的总述和文档正文。改一个值，要把所有复述这个值的地方一起改。
                          2. 一个正确的指针指向一句错话。改动点写着「上限1.5（不再钉1，见文件头）」，文件头却还写着「像素比1」。写明「见X」，等于让下一个人去相信那句错话，所以写「见X」时顺手打开X看一眼。
                          3. 结论还对，理由已经不成立，最难找。里面没有过期数字可以grep，只能在改完一个值后，回头把所有解释这个值为什么是这个值的段落读一遍。
                          
        
                          另外三条
                          • 跨文档引用一条规矩写内容短语，不写编号（编号会错位）。
                          • 撤掉一处实现时，要连带找出哪些数字是在它身上量出来的。
                          • 相似只是线索，不是结论。看到相似的句子不要一起改，每一处单独核对。
