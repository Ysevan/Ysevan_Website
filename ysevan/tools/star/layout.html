布局与自适应

工具类是一条玻璃侧栏加内容区，按1440等比放大、900收顶栏、600换底部tab bar；小屋是一屏名片、一条轨道和一条日记流，内容容器一律不写高度。演示框都是「缩小的视口」：拖宽度、拖高度、切写法，读数是当场量出来的。

用在哪

刷刷、岗岗、plan的桌面形态（card没有侧栏，只有顶栏）。本站侧栏同一个结构：品牌与搜索格在上、外观三行在下，中间的导航单独滚。

为什么

侧栏底部那组是切主题的唯一入口。侧栏按--u等比放大而视口高不跟，刷刷在2040×1019上只剩约24px余量，再挤一点那组就被裁掉，而且不留痕——用户只会以为「没有换色的地方」。刷刷的做法是整条侧栏overflow-y:auto；本站再进一步，只让导航滚，外观控件不用滚就看得见。

坑

导航那段的min-height:0不能省：flex子项默认最小高度是内容高度，不写它导航就把侧栏撑高、自己永远滚不起来。不用scrollbar-gutter: stable：它在所有尺寸都预留一条滚动条位，正常版面也被改了。

坑

clamp的上限要取「它在1440处的实算值」，不能拿设计稿上的整数凑：刷刷1441起改用「1440的设计值×--u」，和clamp在1440处插出来的值对不上，拖过这一格时侧栏244.8→240.2、内容内边距28.8→24、标题34.16→34.02各跳一次。任何宽度都不许出横向滚动条：判据跟目标宽度比，先注入一块撑破的元素让判据红一次。

用在哪

四个工具统一，本站外壳star.css第2节同一条公式。屋主台式2040拿到1.417（没到封顶，填满和严格等比是同一件事）；笔记本2552触到1.45封顶，多出来的宽度（按本站的令牌算464px）只给卡片与列表轨道吃，所以笔记本上构图比Mac紧一些——这是封顶的主动代价，高分屏上正文的物理大小和Mac差不多。

为什么

屋主在Windows大屏上要「跟Mac一样」：构图不变、整体放大。初版抬clamp上限、≥1600拆多列，字只涨1.13–1.18倍、版面涨1.36倍还多一列，整屏变密，不像同一个设计。公式也必须是「视口÷1440」：刷刷写过1440→2560的线性爬坡，两端对、中间偏小，2040处只有1.241（等比给1.417，大14%），整屏小一圈，就是屋主反复说「刷刷跟Mac差距大」的来源。原则见总览「构图不变，等比放大」。

坑

zoom和transform缩放会把边框宽度、文字光栅化、sticky / fixed的定位一起拖下水，zoom还不是标准属性。等比放大只管横向：屋主的屏比Mac扁（宽高比2.00对1.60），按视口高定尺寸的东西不会跟着--u走，要逐个单独决定（见本页「扁视口紧凑排」和「dvh」两条）。

不认三角函数的老内核走台阶，兜底探针写scale:，不写width:

tan(atan2(…))算出来是无单位数，width本来就不收无单位数，拿它当探针在哪个内核里都是假，@supports not就恒真，把台阶值盖到所有浏览器上。scale收无单位数，探针才真的在测「认不认三角函数」。

用在哪

四个工具与本站外壳（star.css第2节，紧跟在公式后面）。老内核走台阶，放大不连续但能放大。

为什么

探针要测的是「这条声明能不能成立」。width: 1.417在任何浏览器里都不成立，所以那条探针测不出任何东西；scale: 1.417是合法值，认三角函数的内核里探针为真、不认的为假，not之后才正好只罩住老内核。

坑

台阶要按屋主的视口排：岗岗2026-09-27以前只写了三档（1600 / 1920→1.33 / 2088封顶），台式2040在老内核上只拿到1.33；改成六档后给1.39，离公式的1.417从差6%缩到差2%。探针错了不报错，只有在认三角函数的浏览器里量--scale才看得出来。

 1、祖先带 backdrop-filter / filter / transform 时，position: fixed 改以它为参照
    → 玻璃卡里要贴底贴顶一律 position: sticky; bottom: 导航高 + 8u；非要 fixed 就挪出玻璃卡
      （演示框里用一个静态 transform 代替磨砂：同一条规则，框里不新增 backdrop-filter）
 2、min-height 的 grid 默认 align-content: stretch，多余空白平均分给每一行 → align-content: start
 3、列 flex 里 margin: auto 顶掉 stretch，子项缩成内容宽 → 显式 width: 100%
 4、flex 两个兄弟各挂一个 margin-left: auto，剩余空间被均分 → 先合成一个右侧组再整体靠右
 5、百分比 padding 参照包含块的宽（品牌字在内约200px），padding: 8% 把34px的图标压到2px
    → 尺寸写死成 calc(var(--brand-box) * .84)
 6、单行输入的值不含换行，浏览器直接吞掉 \n → 「第一行当标题」用 rows="1" 的 <textarea>
 7、figure 默认 margin: 1em 40px → reset 那一行要有 figure：p, h1, h2, h3, ul, ol, li, figure { margin: 0; }
 8、overflow-x: hidden 不显示滚动条，但挡不住 scrollWidth 被顶大（iOS 照样能左右拖）
    → 锚在 right: 0，要往外挪用 right: clamp(0px, 5vw, 84px)；往外挂的装饰必须有收起的断点
 9、overflow: hidden 裁圆角的卡会把挂在它身上的装饰一起裁掉 → 装饰挂在外面那一层
10、只有一行 auto 的 grid，格子不定高，子元素 max-height: 100% 算不出来
    → max-height: calc(100svh - 40px - env(safe-area-inset-top))（封顶用 svh，不再补一行裸 vh）
11、吸顶顶栏的高度只让 html 的 scroll-padding-top 管一次；条目的 scroll-margin-top 只留12px

用在哪

①刷刷「开始练习」底栏（3.11.0–3.12.0手机上滚动途中看不到、滚到底盖住最后一组36px）、plan「更多」面板；②plan的.app-shell（顶栏形态下侧栏那行凭空长出两百多像素）；③card画廊（整条舞台从950缩到594）；④plan分组小标题的动作链接与计数；⑤岗岗品牌图标；⑥plan笔记页「记一条」；⑦⑧⑨小屋门厅；⑩本站的底部弹层（更新记录面板撑到2849px）；⑪本站601–900宽的锚点（768下顶栏下面空76px）。

为什么

这些都不报错，常常只在某一档宽度、滚到中途、或者换一台机器才露馅：只看页面顶部截图、只在开发机上看，三轮验收都没发现第1个。所以每个修法都配了量法：量滚动顶中底三处的位置、量scrollWidth、量计算样式，不靠目测。
