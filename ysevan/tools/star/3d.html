3D与性能

3D在这几个站里只是点缀：叠在静态版上面，没显卡的机器走精简档，扛不住就安静退回。演示大多真跑WebGL：滚到才建上下文、滚走就还给浏览器，同一时间只跑一个；拿不到WebGL的浏览器停在说明，这本身就是这一章讲的降级。

通用

刷刷、岗岗、plan、小屋四处的3D用的是同一套纪律：先有静态版，3D叠在上面；探测、分档、看门狗、限帧、按需渲染、打包，四家一个口径（各家现状不一样的地方逐条写明）。

3D只是点缀：叠在静态版上面，首屏零3D字节，不够格的设备一个字节都不下

页面对3D的每次调用都是发出即走：不等它、不拦点击、不改渲染顺序。3D关着时界面和今天逐像素相同；3D的包等首屏画完、第一次滚动之后的空闲时刻才取。

      为什么

      软件合成下rAF本来就常常不满60拍，按「离上一帧多久」排会被凑成每两拍画一次（约23帧）；按到期时刻排，长期平均仍是30帧。真正让固定4ms容差够用的是「落后超过一个间隔就重新基准」这一句：欠账一旦累积，卡顿之后就会连画补帧或持续跳帧。

      坑

      岗岗中途改过「半拍容差」（max(4ms, 上一拍间隔/2)），理由是固定容差在整页只有10–20拍时会掉到7帧——后来复现不出来，已撤销：建两份只差这一行的副本，在被磨砂拖到30拍以下的一档各跑3次，出帧/拍均值0.63对0.75，区间大幅重叠，当时机器上还有几十个Chrome在跑，这点差别立不住。一个「安全但不存在」的故障，会换来一个永远没人敢删的多余机械。

float bayer2(vec2 a) { a = floor(a); return fract(a.x * .5 + a.y * a.y * .75); }
float bayer4(vec2 a) { return bayer2(.5 * a) * .25 + bayer2(a); }    // 4×4，0..15/16
float th = bayer4(gl_FragCoord.xy) + 1. / 32.;
if (uFadeFlip > .5) th = 1. - th;     // 相邻两件阈值互补（按层的单双）

          抖动是一格格的像素：2倍屏上读作一层细纹理，1倍屏、尤其夜里浅色物件压在深底上看得出网点。它只出现在交接那几十svh里，停留时没有——那是已知代价，不是遗留缺陷，别因为「网点看得见」把这条重开。阈值不互补时两件抢同一批像素：一半像素两件都画（深度定输赢），另一半谁都不画、露出底色。

          坑

          精简档不让灯呼吸：呼吸是停下来之后唯一还在动的东西，留着它render()永远返回true，夜里根本不存在「停稳」，重画没机会发生——这是读代码发现的，不是验收。量这一帧耗时别用gl.finish()：Chrome 153上它不等画完（只读到1.8–2.0ms），紧接着的readPixels还要等17–28ms。验「不闪」要真交出一帧空画面：只改尺寸、隔200ms才画，Chrome会沿用上一帧，判据红不了。
