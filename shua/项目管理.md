## 二、管理原则

1. 每个正式发布包必须有唯一版本号和发布日期。
2. 每项用户可见变化都必须写入更新日志，不能只写“优化若干”或“最新版”。
3. 同一版本正式交付后不得静默替换；任何代码、题库、解析、界面或文档变化都必须产生新的版本记录。
4. 学习记录和题库修改属于用户数据，升级不能以清空浏览器数据作为解决方案。
5. 题库、源码、备份和学习笔记均按内部资料管理，不得上传到无访问保护的公开位置。
6. 发布前必须保留上一正式版本和可用的完整数据备份，以便回滚。

## 三、版本号与发布状态

版本号使用 `主版本.次版本.修订版本`：

- 主版本：存在不兼容的数据结构、题库身份或主要操作流程变化，例如 `2.x.x → 3.2.0`。
- 次版本：新增向后兼容的用户功能，例如 `2.0.0 → 2.1.0`。
- 修订版本：缺陷修复、答案或解析修正、兼容性改进和文档完善，例如 `2.0.0 → 2.0.1`。

发布状态分为：

1. **开发中**：变更写入 `CHANGELOG.md` 的 `[Unreleased]`，不修改正式版本号。
2. **待发布**：功能冻结，确定候选版本号，执行完整测试和数据兼容检查。
3. **已发布**：更新全部版本镜像、填写发布日期并归档交付包。
4. **已归档**：只用于回滚，不再修改该目录中的任何文件。

紧急修复也必须递增修订版本号，不能直接替换已经交付的同名目录。

## 四、版本信息与同步文件

`project.js` 是应用运行时版本信息的权威来源，包含：

- `version`：正式版本号；
- `releaseDate`：发布日期；
- `author`：项目作者；
- `classification`：使用范围；
- `changes`：本次正式版本的用户可见变化摘要。

以下文件是版本信息的镜像或发布配套文件，每次正式发布必须同步：

| 文件 | 必须更新的内容 |
| --- | --- |
| `project.js` | 版本、日期、本次更新摘要 |
| `VERSION` | 纯版本号 |
| `app.js` | 文件头和 `project.js` 缺失时的兜底版本 |
| 九个内置题库脚本 | 生成版本、来源文件、题量和校验元数据 |
| `index.html` | 初始版本角标和静态资源 `?v=` 参数 |
| `manifest.webmanifest` | `version`，不得随意修改稳定的应用 `id` |
| `sw.js` | 文件头、预缓存资源参数、按需清单 `ON_DEMAND` 和新的缓存代次 |
| `effects.js` | 按需 bundle 地址 `BUNDLE_URL = "./effects-3d.bundle.js?v="` 的版本参数，必须与 `sw.js` 的 `ON_DEMAND` 逐字一致 |
| `serve.ps1` | 文件头版本、资源白名单（与 `serve.mjs` 同一份文件清单） |
| `serve.mjs` | 文件头版本、资源白名单和安全响应头 |
| `打开刷刷.bat` / `打开刷刷.command` | 两个平台的独立启动入口，不得包含数据库、小屋或 Docker 启动逻辑 |
| `NOTICE.txt` | 对外显示版本 |
| `README.md` | 当前版本和受影响的功能摘要 |
| `使用说明.txt` | 当前版本及变化后的实际操作方法 |
| `CHANGELOG.md` | 新版本的完整变更记录 |
| `项目管理.md` | 项目基线版本和流程变化 |
| `检查发布版本.ps1` | 版本、日期、更新日志、资源参数和缓存命名的一致性检查 |
| `stats.json` | 题库数与题数，给小屋主站工具页用；由 `scripts/release-check.mjs` 生成，勿手改 |

Service Worker 缓存名是独立的内部代次，例如 `zongfu-quiz-v9`，每次修改预缓存资源都应递增；它不能直接等同于软件版本，也不能重复使用旧缓存名。

3D 点缀从 `v3.11.1` 起只发布一个文件：`effects-3d.bundle.js`（场景 + three 子集 + GSAP 打成的经典脚本，IIFE，全局名 `__shuaFx3d`，626 KB / gzip 172 KB）。`effects-3d.js` 与 `vendor/` 下的 three 子集、GSAP 核心降为**构建输入**（`scripts/release-check.mjs` 里的 `BUILD_INPUTS`）：留在仓库里供重新构建，但不进 `sw.js` 清单、不进 `Dockerfile`、不进两份白名单。改成经典脚本是因为浏览器对 `file://` 禁用 ES module，而屋主在手机上只能直接双击 `index.html`。

bundle 列在 `sw.js` 的 `ON_DEMAND` 里：**不在** install 时预缓存（不拖慢离线安装，也不让不显示 3D 的设备白下载），而是在设备加载成功后由 `effects.js` 通知 Service Worker 补进缓存（消息 `shua-fx-warm`；首次访问时页面还没被接管，只靠 fetch 处理器会漏掉）。离线且没缓存过时，Service Worker 回一个占位**脚本**（`window.__shuaFx3d = { shuaOffline: true };`——按需文件是经典脚本，占位里写 `export` 会当场语法错），页面安静地退回平面界面。所以 bundle 内容有任何变化都必须递增缓存代次。

场景代码改了就要重跑 `node scripts/build-3d-vendor.mjs --modules <目录>` 重新生成 bundle；升级 three / GSAP 或增减 three 符号时同理，改脚本里的常量与符号清单后重新构建。依赖装在本机磁盘的临时目录里，不要装进刷刷目录或网络卷。

应用版本与数据格式版本相互独立。`localStorage` 键名、备份文件中的 `version: 1/2`、题库格式版本等不得仅因为软件版本变化而随意修改。

## 五、更新日志制度

### 1. 开发阶段

每完成一项变化，立即写入 `CHANGELOG.md` 的 `[Unreleased]`。固定分类如下，无内容的分类可省略：

- 新增
- 变更
- 修复
- 兼容性
- 安全
- 文档

记录必须说明“用户能看到什么变化”和“影响哪些数据或操作”，避免使用含义不清的描述。

### 2. 正式发布

发布时把 `[Unreleased]` 中的内容移动到新的版本条目，并填写日期：

```text
## [2.0.1] - YYYY-MM-DD

### 修复

- 修复……问题；影响……页面，不改变已有学习记录。

### 兼容性

- 继续兼容……格式；无需用户迁移数据。
```

随后重新保留一个空的 `[Unreleased]` 区域，供下一轮开发使用。

### 3. 每次更新必须填写的信息

| 字段 | 要求 |
| --- | --- |
| 版本号 | 唯一且符合版本规则 |
| 发布日期 | `YYYY-MM-DD` |
| 更新摘要 | 面向用户的简洁说明 |
| 影响范围 | 页面、题库、记录、备份或启动方式 |
| 数据兼容 | 是否兼容旧记录和旧备份，是否需要迁移 |
| 验证结果 | 完成的语法、功能、设备和导入导出测试 |
| 已知问题 | 未解决限制及临时处理方式 |
| 回滚方式 | 对应上一版本目录和数据恢复方法 |

## 六、标准更新流程

1. 明确需求、影响范围和数据兼容风险。
2. 将计划中的用户可见变化写入 `[Unreleased]`。
3. 修改程序、题库或文档，不覆盖原始题库来源文件。
4. 执行语法检查、题库校验和功能测试。
5. 使用旧版浏览器记录和旧版 JSON 备份执行兼容测试。
6. 确定正式版本号及发布日期。
7. 更新第四节列出的全部版本文件。
8. 把 `[Unreleased]` 变化整理到正式版本条目。
9. 运行 `node scripts/release-check.mjs`：从题库文件实点题数、重新生成 `stats.json`，并核对整张资源图——页面脚本与样式带同样的版本参数进了 `sw.js` 预缓存；预缓存与按需清单的每个文件都真实存在、进了 `Dockerfile` 和 `serve.mjs` / `serve.ps1` 两份白名单；`vendor/` 下没有漏登记的文件；3D 按需模块的地址、它引用的 three 符号和第三方许可注释都对得上。
10. 运行 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\检查发布版本.ps1`。
11. 完成发布检查清单并记录已知问题。
12. 复制完整发布目录，按标准名称归档，正式目录发布后设为只读基线。

## 七、发布检查清单

### 代码与数据

- JavaScript 文件全部通过语法检查。
- `serve.ps1` 通过 PowerShell 语法解析，`serve.mjs` 通过 Node.js 语法检查。
- 内置题库总数、题型数量和题目 ID 唯一性正确。
- 每道题均可读取题型、题干、选项、答案和解析。
- 页面、`project.js`、`VERSION`、清单、说明和日志版本完全一致。
- `检查发布版本.ps1` 返回“发布版本检查通过”。
- `node scripts/release-check.mjs --check` 通过：`stats.json` 与题库文件一致，资源图核对全部通过（含 `vendor/` 与 3D 按需清单）。
- Service Worker 使用新的缓存代次和正确的资源参数；3D 按需文件内容有变化时同样递增了代次。

### 功能

- 首页、连续刷题、专项练习、模拟考试和自动看题可用。
- 上一题、下一题、提交答案、解析、计时和交卷逻辑正确。
- 错题、不会、收藏、笔记、已掌握和间隔复习正确。
- 多题库创建、导入、导出、切换、重命名和删除正确。
- 各题库的学习记录、连续刷题断点、自动看题断点和未完成会话相互隔离。
- 自动看题断点：同一批题目默认续上并提示，题目集合变化后从第 1 题开始并提示；看到最后一题再完成看题则回到第 1 题。
- 存在「答过题、未结算」的练习或模拟考试时，`startSession` 与 `startReviewSession` 入口（含「连续刷题」入口）先确认再覆盖，确认窗排在「这次怎么刷」之前且只问一次；取消后原会话的题号和已答数不变。被顶掉的是连续刷题或自动看题时不确认（位置另存，不丢东西）。
- 专项练习默认使用单个题库，可直接选择任意题库；混合模式至少选择两个有题目的题库。
- 混合题库的题型、难度、题量、随机/顺序、逐题反馈、统一交卷和自动看题均可用，并显示题目来源。
- 混合会话使用题库与题目的复合标识；答题、错题、不会、收藏、笔记和统计分别写回来源题库，相同题目 ID 不串记录。
- 混合练习退出、刷新和“继续上次”后仍可恢复当前位置、答案和判分；上一题可回看且不重复计分。
- 完整备份可导出，并能在空白浏览器环境中恢复。
- 旧版单题库记录和旧备份格式仍可读取或有明确迁移方案。
- 3D 点缀开启时：首页题库牌堆可翻看并切换题库，做题小牌堆随答对/答错正确反应且模拟考试不透露对错，结算落堆正常；连点「下一题」不被动画拖住。
- 3D 点缀关闭（“数据管理 → 界面动效”或系统减弱动态效果）时，各页与未加 3D 时一致，且不下载 3D 组件。

### 设备与界面

- 桌面宽度下主要页面无溢出。
- 320px 和 390px 手机宽度下主要按钮可见、可点击。
- 768px 竖屏平板使用移动布局且操作按钮不丢失。
- 鸿蒙、Android 和 iPhone/iPad 的现代系统浏览器可完成核心刷题。
- iPhone 安全区、动态视口、弹窗和底部导航布局正常。

### 启动与安全

- Windows / macOS 的 `打开刷刷` 启动器均位于刷刷文件夹内，能打开正确页面，且不连接小屋或数据库；关闭服务窗口后服务停止。
- 局域网地址只在可信专用网络中使用，不映射到公网。
- 本地服务资源白名单无法读取源码说明以外的非公开目录文件。
- 禁止索引、安全响应头和内部使用声明仍然存在。
- 发布包不包含真实学习笔记、测试备份或临时文件。

## 八、题库变更管理

1. 原始 Excel 文件由维护者在受控位置另行归档，不随网页发布目录公开分发。
2. 归档记录至少包含来源文件名、取得日期、题量、题型数量和文件校验值。
3. 生成或转换题库时不得覆盖原始文件。
4. 题目 ID 必须保持稳定；如必须变化，先制定旧学习记录迁移方案。
5. 修正答案、题干或解析时，在更新日志中写明影响题量、题型和原因。
6. 批量导入前先在副本中验证，确认无重复 ID、空题干、越界答案和无效选项。

## 九、数据兼容与迁移

修改学习记录、题库注册表或备份结构时必须：

1. 保留旧字段读取能力；
2. 在加载阶段执行可重复、不会清空数据的迁移；
3. 将不同题库的记录继续隔离，避免相同题目 ID 串数据；

5. 失败时保留原数据，并给出可理解的错误提示；
6. 在更新日志中说明兼容范围、迁移方式和不可逆影响。
