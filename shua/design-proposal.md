# 刷刷 UI 打磨建议方案

- 适用版本：v3.8.3
- 方案定位：**不改版、不动信息架构、不动交互流程**，只做可单条采纳的小幅美化与缺陷修补
- 审阅方式：每条建议独立编号，可单独批准或否决；未获批准的条目不实施

## 一、设计现状小结

### 1. 现有视觉语言

| 维度 | 现状 |
| --- | --- |
| 主色 | `--red: #b4232c`（酒红），深色态 `--red-dark: #8d1821`，浅底 `--red-soft: #fff1f1` |
| 语义色 | 绿 `#18794e` / 琥珀 `#a35b00` / 蓝 `#245ea8`，各配一个 `-soft` 浅底，成对使用 |
| 中性色 | `--ink #202124` / `--muted #687077` / `--line #dde1e5` / `--surface #fff` / `--canvas #f5f6f7` |
| 深色面 | 侧栏 `#25282c`、首页今日面板 `#303439`（两个不同深灰，均未进变量） |
| 圆角 | 3 / 4 / 5 / 6 / 7 / 8 / 10 / 12 / 13 / 999px / 50%，共 11 种 |
| 阴影 | 仅 `--shadow` 一个 token，用于 `.mode-button:hover`、`.toast`；面板一律"描边不投影" |
| 字号 | 10 – 42px，十七档，均为 px；仅 `.keyboard-tip`（`styles.css:164`）用 `.78rem` |
| 字重 | 650（2 处）/ 700（17 处）/ 750（4 处） |
| 品牌 | 纯文字「刷刷」+ 副标「离线刷题工具」，v3.6.2 已移除图形 Logo |

### 2. 做得好、不要动的地方

1. **色彩语义一致**：正确=绿、错误/主操作=红、提示=蓝、记忆锚点=琥珀，全站没有例外。`.option.correct` / `.feedback.good` / `.search-options li.is-correct` / `.summary-answer.correct` 用的是同一套绿。
2. **克制的平面风格**：面板统一 `1px 描边 + 白底 + 小圆角`，没有滥用投影和渐变，长时间刷题不刺眼。这是本项目最值得保留的特征。
3. **移动端触控目标已被系统性补齐**：`styles.css:433/434/454/458/469/474/517` 逐条把按钮、图标按钮、分段控件、快捷选题按钮抬到 44px，说明 44px 规则已经被认真执行（本方案只补三处漏网的）。
4. **安全区处理到位**：`.mobile-header`、`.mobile-nav`、`.form-footer`、`.question-footer`、`.toast` 都用了 `env(safe-area-inset-*)`，`.question-surface` 还做了 `@supports (height: 100dvh)` 兜底。
5. **reduced-motion 已实现**：`styles.css:526-529` 全局关闭过渡并单独关掉滑动动画。
6. **滑动切题的视觉反馈完整**：`.swipe-preview` 的左右预览卡 + `.swipe-content.is-swiping` 的抬起阴影，是一套完成度很高的手势反馈，不要碰。
7. **空状态齐全**：搜题、错题、题库管理都有 `.empty-state` 分支，没有出现空白页。

**结论：本项目不需要改版。** 下列问题全部是局部缺陷或 token 层面的碎片化，不涉及视觉方向。

### 首页 `renderHome`（app.js:693-748）

- **P1｜今日面板两个按钮 hover 后文字几乎不可见。** `.today-actions .primary`（`styles.css:75`，特指度 0-2-0）只覆盖了静态态的 `background/color`，但 `.button.primary:hover`（`styles.css:58`，特指度 0-3-0）仍然生效。结果：静止时是"白底红字"，hover 时背景被改成 `--red-dark #8d1821`、文字仍是 `--red #b4232c`，**对比度约 1.4:1**。`.today-actions .secondary`（`:76`，白字透明底）hover 时被 `.button.secondary:hover`（`:60`）改成 `#f0f2f3` 近白底，白字对白底，**对比度约 1.06:1**。这是全站最显眼的主 CTA。
- **P2｜320px 下描述文字可能被按钮压住。** `.today-actions` 是 `position: absolute`（`:74`，移动端 `:442`），不占面板高度；而 `resumeDescription`（`app.js:701`）会拼接完整题库名，如"【新】2026年度综合服务经理岗位准入资格年检题库"。在 320px 宽、`.today-panel` 仅 `min-height: 222px` 的情况下，该段落可占 4 行，正文底边会落到按钮区域之内。
- **P3｜手机端完全看不到每日目标。** `.goal-panel { display: none }`（`:444`）在 ≤900px 隐藏目标环，侧栏进度条同时也被隐藏。但数据管理页文案写着"首页会按目标显示当天完成进度"（`app.js:2223`）——在手机上这句话不成立。
- **P4｜`.mode-button:hover` 的 `transform: translateY(-1px)` + `box-shadow`（`:103`）没有任何 transition，抬起是瞬间跳变**。全站 hover 态（`.nav-item`、`.option`、`.button`、`.resume-item`）同样没有过渡。

### 移动端导航 `renderNav`（app.js:636-651）

- **P16｜底部导航是 5 列网格，但只有 4 个按钮。** `renderNav` 产出 3 个主项（home / practice / search，`app.js:641`）+ 1 个"更多"触发器 = 4 个在流子元素；`.mobile-more-sheet` 是 `position: fixed`（`:428`），不占网格单元。而 `.mobile-nav { grid-template-columns: repeat(5, 1fr) }`（`:424`）。**结果是底栏四个按钮偏左排列，右侧永久空出五分之一**。应为历史遗留。
- **P17｜底部固定元素有三套不同偏移。** `.question-footer` / `.form-footer` 用 `bottom: calc(62px + env(...))`（`:461`、`:477`），紧贴导航无间隙；`.mobile-more-sheet` 用 68px（`:428`）；`.toast` 用 76px（`:523`）。同时 `.main-content { padding-bottom: 68px }`（`:419`）是唯一没有加 `env(safe-area-inset-bottom)` 的方向（同一行的 `padding-top` 加了），iPhone 上导航实际高度是 `62 + 34 = 96px`，靠 `.view` 额外的 36px 下内边距才勉强不遮挡。
- **P18｜"更多"有两个入口。** 顶部 header 的 `#mobile-more`（`index.html:33`，`app.js:2720`）和底栏的 `.mobile-more-trigger`（`app.js:644`）打开同一张面板，而面板锚定在底部（`:428`），从顶部按钮打开时存在空间错位。**属交互问题，见"暂缓"。**

### 全局

- **P20｜焦点环在深色面上几乎不可见。** `outline: 3px solid rgba(36, 94, 168, .24)`（`:28`）是 24% 不透明度的蓝，叠在侧栏 `#25282c` 上基本看不出来；`.scope-bank-option input:focus-visible + span`（`:135`）却用了不透明的 `2px solid var(--blue)`，两套并存。
- **P21｜数字无等宽对齐。** 只有 `.quiz-count, .quiz-timer`（`:144`）设了 `font-variant-numeric: tabular-nums`。会实时变动的 `.metric strong`、`.goal-ring strong`、`.sidebar-goal-line strong`、`.bar-row strong`、`.day-column strong`、`.summary-metrics strong` 都没有，答题过程中数字宽度会抖动。
- **P22｜reduced-motion 下仍有平滑滚动。** `styles.css:527` 的 `scroll-behavior: auto !important` 管不到 JS：`app.js:673` 每次 `navigate()` 都调用 `window.scrollTo({ top: 0, behavior: "smooth" })`，该参数由 JS 指定，不受 CSS 约束。
- **P23｜token 覆盖率低。** 全表 72 个不同十六进制色值，其中只有 16 个在 `:root`。仅"红色系描边"一类就有 `#c58086 / #c78e93 / #d8a6aa / #d9a0a5 / #dcaeb3 / #dd999e / #e0a5aa / #e5c5c8 / #f0d5d8 / #f2c7ca` 十个各用一两次的一次性值，职责完全相同（选中态/hover 态描边）。
- **P24｜字重 650 / 750 在实际字体上无效。** 字体栈首位是 `"Microsoft YaHei"`（`:18`），Windows 上仅有 Light/Regular/Bold 三档，650 与 750 都会落到 Bold，与 700 渲染完全一致——区分是名义上的。
- **P25｜图标尺寸有 5 档**（16 / 17 / 18 / 19 / 34px），16 与 17、18 与 19 在视觉上无法区分。

## 四、不建议做的事

以下是常见的"美化"手段，在本项目**明确不应采纳**：

1. **引入任何 CSS 框架或工具链**（Tailwind、Bootstrap、Sass/Less、PostCSS）。项目定位是"纯静态前端、无构建工具、样式集中在单个 `styles.css`"，引入构建产物会破坏 `serve.ps1` 白名单与 `sw.js` 预缓存清单的一一对应关系。
2. **引入外部字体或 CDN 资源**（Google Fonts、iconfont CDN、任何 `https://` 资源）。`serve.ps1:67` 的 CSP 是 `default-src 'self'`，`style-src` 也仅放开 `'self' 'unsafe-inline'`，外部资源会被浏览器直接拦截——不是"效果差一点"，是**完全加载不出来**。若确需自定义字体，必须自托管字体文件，并同步加入 `sw.js` 的 `FILES` 数组与 `serve.ps1` 的 `$publicFiles` 白名单，且要评估字体文件体积对离线缓存的影响；不推荐。
3. **加回图形 Logo / 应用图标插画**。v3.6.2 已明确移除，品牌就是纯文字「刷刷」。A8 只是清理已经失效的 `.brand img` 规则，不是为加回图形做准备。
4. **玻璃拟态、大面积渐变、彩色阴影、霓虹描边等风格化处理**。与"描边不投影"的现有语言冲突，且长时间刷题场景下会增加视觉疲劳。
5. **更换图标库**。Lucide 已本地化在 `vendor/lucide.min.js` 并进了预缓存与白名单，替换需同步改三处清单 + 全量核对 `data-lucide` 名称，收益为零。
6. **引入动画库或增加页面转场动画**。现有滑动切题手势与 `prefers-reduced-motion` 支持是精心调过的，任何全局动画都可能与 `.swipe-content` 的 transform 冲突。
7. **把 `styles.css` 拆成多个文件**。每个新文件都要进 `sw.js` 预缓存清单、`serve.ps1` 白名单、`index.html` 的 `?v=` 参数，还要递增缓存代次——维护成本高于收益。
8. **暗色模式**（见 C2）。若日后确要做，应作为独立的次版本立项，而非混在打磨里。

## 六、3D 纸卡点缀（2026-09-20 追加）

- 基线：v3.9.1（`offline` @ `271e4e9`）。技术栈由屋主指定：WebGL + Three.js + GSAP，鼠标与滚动触发交互。
- 来由：小屋主站工具页的 3D 试点把刷刷做成「一叠被刷走的纸闪卡」，屋主满意，希望各工具本身也有。
- 本章是方案，写完即实施（屋主已明确不必等审批）。实施后以代码与 `CHANGELOG.md` 的 `[Unreleased]` 为准。

### 1. 原则

1. **3D 是点缀，答题主流程一步不多、一毫秒不等。** 页面对 3D 的每次调用都是「发出即走」：不 `await`、不拦点击、不改变任何渲染顺序。动画没播完就点下一题，动画直接跳到终点，不排队。
2. **叠加，不替换。** 3D 只出现在三个新增的槽位里。槽位在 2D 模式下 `display: none`，2D 界面与今天逐像素相同；降级的终点永远是今天这套界面。
3. **同一种纸。** 着色的做法照搬小屋工具页那叠闪卡（`Ysevan_web` 的 `components/tool-3d/scene/paper.ts`）；纸色自 v3.11.0 起对齐界面上的半透明白卡：卡纸白 `#FFFFFF`、偏冷的次白 `#F6F7FB`、淡灰蓝纸边 `#D9DEEA`（墨色同时改为 `#1F2333`）；漫反射量化成三档平涂，背光掺一点海湾蓝冷影；程序化纸纤维（亮度 ±3%）；贴边一圈颜料边；柔边椭圆假投影。不用 PBR 写实材质，不开实时阴影，没有模型文件和 loader。
4. **身份色 `#B4232C` 每个场景只点一处：手写的那个勾**，和工具页刷刷闪卡背面那个勾是同一个东西。答错的记号用淡墨 `#3E3C35`。

### 2. 三个落点

| 落点 | 位置 | 呈现 | 鼠标与滚动 |
| --- | --- | --- | --- |
| 首页题库牌堆 | 首页深色「今日复习」卡的右侧；视口 ≥1180px 才出（更窄时右侧没有富余位置，宁可不出也不挤文字） | 每个题库一张卡，当前题库在最上面；卡面写题库名与题数，勾只写在当前题库那张；题库名按词折行（中文逐字可断，英文单词、数字不拆开，单词比整行还宽时才逐字断） | 牌堆随指针轻倾；点牌堆，最上面那张被「刷」走、翻面塞回最底，下一张顶上来；翻到不是当前题库的卡时，下方出现「切换到这个题库」按钮。页面滚动时牌堆后仰、微微散开 |
| 做题小牌堆 | 做题页顶栏题数右侧的小槽 | 本轮剩余题目的一叠薄卡 | 提交答案：答对→翻面、写出勾、刷走；答错→翻面、淡墨记号、从牌堆上方越过去塞回牌堆底（错题会再回来）。模拟考试与自动看题翻页只滑走不翻面，**不泄露对错**。连续刷题刷完一轮，牌堆重新发满。槽位左边就是题数，卡只往右、往上动，任何一帧都不越过槽位左缘；画布只向左多 6px，比题数与槽位的间距（手机 10px、桌面 18px）小，几何上就盖不到题数 |
| 结算落堆 | 结算页分数圈上方一条 | 本轮的卡（最多 12 张）依次落下：答对的码成整齐一叠，答错的歪着另成一小叠（待重练）；最后在答对那叠顶上写出勾（一道没对就不写） | 牌堆随指针轻倾；往下滚到错题回顾时后仰 |

槽位里的可点部分都是真正的 `<button>`（翻看下一张、切换题库），能用键盘操作；画布本身 `aria-hidden`。

### 3. 加载与体积

- **首屏零 3D 字节。** 页面只多一个经典脚本 `effects.js`（判定与调度，几 KB）。three、gsap 和场景代码在首页渲染完、浏览器空闲时才取；不够格的设备一个字节都不下载。
- **加载方式：v3.11.1 起从 `import()` 改成注入经典脚本 bundle。** 原来 `effects.js` 用 `import()` 取 ES module 场景，`file://` 下必然失败，所以当时干脆在 `blockedReason()` 里把 `file:` 判成不支持。屋主在手机上只能直接双击 `index.html`，于是改成：`scripts/build-3d-vendor.mjs` 把场景与两个 vendor 子集用 esbuild 打成 IIFE 的 `effects-3d.bundle.js`（全局名 `window.__shuaFx3d`，626 KB / gzip 172 KB），`effects.js` 用 `<script src>` 注入它，`load` 事件后取全局对象，`error` 或 10 秒超时就 `fail("load-failed")`。经典脚本在 `file://` 下照常执行，http 与 `file://` 走同一条路，不维护两套。CSP 的 `script-src 'self'` 放行同源 `<script src>`，三处 CSP 一个字没改。不用 importmap：内联 importmap 算内联脚本，会被同一条 CSP 拦下。
- **three 用按需子集。** three 0.186.0 的发行文件只有未压缩的 `three.core.js` + `three.module.js`（共 2.1 MB）。`scripts/build-3d-vendor.mjs` 用 esbuild 只打场景用到的符号：实测整包压缩后 742 KB（gzip 189 KB），子集（最终 17 个符号）547 KB（gzip 140 KB）。GSAP 3.15.0 只取核心 `gsap-core.js`（不含 CSSPlugin 和插件，场景只补间普通对象），51 KB（gzip 20 KB）。三者都是本地 `vendor/` 文件，不从 CDN 取。
- **许可注释保留。** three（MIT）与 GSAP（GreenSock 标准免费许可，禁止删改版权声明）源码里的 `@license` 注释由 esbuild 原样保留，文件头另加来源说明与 MIT 全文；`NOTICE.txt` 增第三方组件一节。
- **离线。** bundle **不进** `sw.js` 的 install 预缓存——既不拖慢离线安装，也不让减弱动效的设备白下载——而是列在 `ON_DEMAND` 里（v3.11.1 起只有它一项）：够格的设备加载成功后，`effects.js` 通知 Service Worker 把它补进缓存，之后离线也有 3D。（实施时发现只靠 fetch 处理器会漏：首次访问时页面还没被 Service Worker 接管，那一次加载不经过它。）离线且从没加载过 3D 时，Service Worker 回一个占位**脚本** `window.__shuaFx3d = { shuaOffline: true };`，页面安静地退回 2D，控制台不报错——按需文件改成经典脚本后，占位里原来那句 `export const shuaOffline = true;` 会当场语法错，这一条必须跟着改。`file://` 下没有 Service Worker，所以有 3D、没有离线安装。
- **三处覆盖一处不漏。** 发布的文件全部进 `Dockerfile`、`serve.mjs` 与 `serve.ps1` 的白名单、`sw.js`（`FILES` 或 `ON_DEMAND`）。v3.11.1 起 `effects-3d.js` 与两个 vendor 子集是 `release-check.mjs` 里的 `BUILD_INPUTS`：留在仓库供重新构建，但**必须不出现**在上面任何一处（脚本会反过来拦）。脚本另外核对 bundle 存在、含两段许可注释与全局名 `__shuaFx3d`、`effects.js` 的 `BUNDLE_URL` 与 `ON_DEMAND` 逐字一致、`effects.js` 里不再有 `import()`，以及场景引用的 three 符号都在子集里。

### 4. 降级

**三档（v3.11.2 起；此前只有「完整 / 平面」两档，只有软件渲染的机器一律平面）。**

| 档 | 什么机器 | 怎么判 | 画什么 |
| --- | --- | --- | --- |
| 完整 3D：高档 / 均衡档 | 有显卡 | 严参数（`failIfMajorPerformanceCaveat: true`）拿到 WebGL2 上下文 | 高档：像素比 ≤1.75、纸纹、几何细分 8、跟指针轻倾与滚动后仰。均衡档（`deviceMemory ≤ 4`、核数 ≤4 或触屏起步，或本次会话降过档）：像素比 ≤1.25、关纸纹、细分 4 |
| 精简 3D：`soft` | 没有独立显卡、只有软件渲染（Windows 的 WARP；带 `--enable-unsafe-swiftshader` 的 Chrome 的 SwiftShader） | 严参数拿不到；同样参数只把 `failIfMajorPerformanceCaveat`、`antialias` 改成 `false`，换一块新画布再取一次，拿到了 | 像素比 ≤1、画布物理像素长边 ≤640（CSS 尺寸不变）、出帧限 30、关纸纹、细分 4、不开抗锯齿、**不跟指针、不随滚动**；投影、张数、卡面字与均衡档相同 |
| 平面 | 两段都拿不到，或命中下面任一条 | — | 原来的 2D 界面，槽位不占位 |

命中任一条即完全 2D，不出任何槽位：

- 用户在「数据管理 → 界面动效」关掉 3D（只存本机，不进备份）；
- 系统开启减弱动态效果（运行中打开也立即拆掉 3D）；
- 省流量模式（`navigator.connection.saveData`）；
- 低端设备：`deviceMemory ≤ 2` 或 `hardwareConcurrency ≤ 2`；
- 浏览器没有 `WebGL2RenderingContext`，或两段都拿不到 WebGL2 上下文（`no-webgl`；例如 Chrome 122 起默认不给 SwiftShader 的 WebGL）。这时顺手探一次宽松参数的 WebGL1，只记进 `status().probe` 供诊断，**不为它做场景**；
- 模块加载失败或超时、WebGL 上下文丢失；
- 运行中出帧太少：一个窗口 = 最近 40 个帧间隔，算窗口的**平均出帧率**（40 ÷ 窗口总时长），低于这一档目标帧率的固定比例算一个慢窗口——精简档目标是自己限的 30 帧、线在 0.6×30 = 18 帧；高档 / 均衡档不限帧，目标取**屏幕实际刷新率**的估计（窗口内间隔的第 5 百分位，夹在 30～120 帧之间）、线在 0.55×目标；两档都再加一条「出帧 ≥50 帧一律不算慢」的上限，免得高刷屏上忽快忽慢时按估出的 120 帧要求、误把好机器降档。高档攒够 1 个慢窗口先降到均衡档，均衡档再攒够 1 个就关掉；精简档没有下一档，要**连续两个**慢窗口才关掉，「超过多久不算一帧」的上限也由 250ms 放宽到 1 秒（软件渲染真扛不住时单帧就可能超过 250ms，不放宽守卫永远攒不满样本）。关掉后本次会话记住（sessionStorage `shua-fx-tier=off`）。
  - 为什么是比例而不是绝对毫秒：原来按「40 帧间隔的中位数 > 28ms（精简 66ms）」判，卡顿让间隔成双峰分布、中位数只落在常见值上，看不见长尾——「60Hz 屏每 4 帧一次 120ms 卡顿」真实只有 22.0 帧却判正常；而 30Hz 屏上完全流畅的 30.1 帧因为 33.3ms > 28ms 判慢、把 3D 关掉。平均出帧率连续、不在量化台阶上翻面，目标又按屏幕自己的节奏取，两种错都不犯。
  - 判据的已知盲区：只看 rAF 间隔分不出「30Hz 屏上流畅」与「60Hz 屏上每帧都要 33ms」——两者的间隔序列一模一样。取「不关 3D」这一边，代价是高档下**匀速**的 16.5～30 帧（0.55 × 夹住的下限 30）不会被判慢；有长尾的卡顿照样判得出来，因为窗口里的快帧暴露了屏幕的真节奏。**为什么盲区落在这一侧（2026-09-23 控制室立的四家通用规矩）：两种错的代价不对等时，往后果轻的那边错。**误判会关掉一台好机器上的 3D，而且 `fail("slow")` 是整个会话记住的；漏判只是让一个匀速偏慢、本来还能看的画面继续跑。上面那条 `FRAME_GAP_LIMIT_MS` 丢弃超长卡顿不放宽，用的是同一条规矩：放宽会让被浏览器节流的后台标签页被误判成慢机器。

（`file://` 打开从 v3.11.1 起已不是降级条件，见第 3 节。）

**精简档只看这一次探测。** 用的是宽松那次拿到的上下文，就一律精简档：完全不看内存、核数和指针，也不读 sessionStorage 里记的档位。屋主那台没显卡的台式（Edge 153 + WARP，`deviceMemory` 32、20 核、DPR 1.25、有鼠标）按高 / 均衡的判法会得高档——软件渲染跑高档就是灾难。反过来，有显卡的机器（屋主的 RTX 4060 笔记本）在第一段就拿到严格上下文，`stage` 为 `strict`、`software` 为 `false`，档位照旧按 `startTier()` 判，精简档的逻辑碰不到它。

**整条判定链不依赖存储成功。** `file://` 下 Safari 读 `localStorage` 直接抛 `SecurityError`。`effects.js` 的每一处读写都包在 try/catch 里：偏好读不到按「开」，`shua-fx-tier` 读不到按「没记过」，本机成功过的记号 `shua-fx-ok` 读不到只是首屏不预留、3D 到了再撑开槽位，写不进去只是记不住。实测把两种存储的读取都改成抛 `SecurityError` 后，精简档照常 active、控制台零错误。

**`ShuaFx.status()` 暴露探测链**：`tier`（当前档，没有场景时为 `null`）、`stage`（`strict` / `loose` / `webgl1-only` / `none`，没探测过为 `null`）、`software`、`renderer`（`WEBGL_debug_renderer_info`）、`probe`（`webgl2Strict` / `webgl2Loose` / `webgl1Loose`，没试到为 `null`）。数据管理页据此显示一行人话和一行探测结果，反馈问题时截这一段就能定位。

**精简档为什么只砍这几样（实测，本机 Chrome + SwiftShader，屋主视口 2040×1019@1.25）。** 投影、双面两遍、叠卡张数减半、纸纹、画布分辨率、抗锯齿这几项在不限帧时逐项开关（无头 Chrome），首页连续翻牌的出帧都在 9–13 帧之间晃，差别在噪声里——瓶颈根本不在 WebGL。真正的大头是**软件合成下的玻璃模糊**：3D 关着、只让一个 24px 小方块在「今日复习」玻璃卡里每帧变色，有窗口的 Chrome 就掉到约 4 帧（放在不压玻璃的角落则是 120 帧）；把全站 `backdrop-filter` 与光晕的 `filter` 去掉，精简 3D 立刻稳定 30 帧、页面 100 帧。所以精简档只做两件事：少画像素、少出帧（限 30、不跟指针、不随滚动——鼠标在首页大卡上画圈时，页面由约 10 帧回到约 48 帧），其余画质按控制室「帧率够就别再砍」保留。无头 Chrome 的软件合成每帧整屏重画（小方块放在角落也掉到 10 帧），比有窗口时悲观，量合成开销时要用有窗口的浏览器。软件合成下玻璃要不要关是界面层的决定，这里没有动。

渲染纪律：全站一个 WebGL 上下文、一块画布，在三个槽位之间移动；只在动画或指针阻尼进行中出帧，静止时零帧；标签页隐藏时停。

槽位的版面**只在 3D 能成的时候**才撑开，加载不成就始终不占位：

- 本机从没成功加载过 3D：首次渲染不预留，3D 真正就绪后才给 `<html>` 加 `fx-ready` 撑开槽位（首页右侧用 0.3 秒过渡）。每台设备只在第一次成功时发生一次。
- 本机成功加载过（`localStorage` 记号 `shua-fx-ok`）：`effects.js` 在首次渲染前同步加上 `fx-ready`，槽位从一开始就在，3D 到了直接淡入，零跳动。这时 3D 文件已在离线缓存里，几乎必成。
- 记号在、这次却失败（例如缓存被清过又离线）：收回一次并清掉记号，之后不再预留。实测收回发生在首次渲染后约 10 毫秒内。

（实施时的取舍：最初是「判定通过就预留」，离线且没缓存过的设备每次打开都会先预留再收回；如果改成「一律加载成功后才撑开」，因为 3D 总在首屏之后才到，每次打开页面都会在约 1 秒后跳一下。按设备记住成功与否，两种跳动都避开了。）

### 5. 验收

- 关掉 3D（开关或减弱动效）后，各页与改动前截图一致。
- 提交答案到反馈出现：3D 开、关两种情况下同样即时；连点「下一题」不被动画拖住。
- 首次打开页面加载的 JS 只多 `effects.js`；three、gsap 只在空闲后、且只在够格的设备上下载。
- `node scripts/release-check.mjs --check` 通过，并做突变自测：删掉任意一个白名单或清单项，它会拦。
- 离线：在线加载过 3D 后断网刷新，3D 仍在；从没加载过的设备断网打开，2D 正常。
- 三档：默认 GPU 的无头 Chrome 为 `stage: strict`、`software: false`、`tier: high`；加 `--disable-gpu --use-gl=swiftshader --enable-unsafe-swiftshader` 为 `stage: loose`、`software: true`、`tier: soft`（再伪装 32G / 20 核也仍是 `soft`），三个画布物理长边 ≤640；去掉 `--enable-unsafe-swiftshader` 为 `reason: no-webgl`、`stage: none`、无画布、控制台零错误。
- 存储不可用：两种存储的读取都抛 `SecurityError` 时，精简档仍 active、控制台零错误。

### 7.1 真源

视觉真源是两份只读文件，已复制进仓库：

- `docs/design/SPEC-apple-glass.md` —— 四个工具通用的规格（结构、颜色、主题与切换、自适应、降级与可访问性、图标、品牌图标、交付）。
- `docs/design/shua-glass.html` —— 按刷刷首页画的样张，浏览器直接打开；`?mode=dark`、`?accent=green|indigo|orange|pink|teal` 看变体，拖窗口看自适应。

改颜色、改结构先改这两份，再改 `styles.css`。`docs/` 不进 `serve.mjs` / `serve.ps1` 白名单，也不进 `Dockerfile`——`scripts/release-check.mjs` 只管 `vendor/` 和被页面真正引用的资源，设计文档不属于运行时资源。

### 7.2 落到刷刷时自己拿的决定

**token 分三层，同一个值只写一遍。** `:root` 里放浅色一组（`-l` 后缀）和深色一组（`-d` 后缀）的字面值，六个 `html[data-accent]` 块里放各自的浅 / 深字面值，最后三段「映射」把 `-l` 或 `-d` 接到样式真正引用的名字上。深色映射出现两次（手动深色 `html[data-mode="dark"]`、自动档 `@media (prefers-color-scheme: dark) html[data-mode="auto"]`），但两处都只写 `var(--x-d)`，颜色值本身仍然只有一份。

**填充档与文字档分开。** `--accent` / `--accent-2` / `--red` / `--green` / `--orange` 用苹果系统色原值，只给填充、渐变、图标底块、色点、焦点环、进度条和背景光晕；凡是写在 `color:` 上的一律换成 `--accent-text` / `--red-text` / `--green-text` / `--orange-text`，取苹果 HIG「增强对比度」那一组。原因是系统色原值当文字都不达标：`#007AFF` 压白 4.02、`#FF3B30` 3.99、`#34C759` 1.90。HIG 的浅色绿 `#248A3D` 实测也只有 4.40，四家统一改用 `#1F7A36`；深色靛 `#7D7AFF` 压在深色玻璃的合成底上只有 4.03，提亮到 `#8E8BFF`（4.67）。

**承载文字的浅底改成不透明。** 次按钮、选中项、标签、计数胶囊、答对 / 答错反馈这些「底上要压文字」的地方，如果用半透明色叠在玻璃叠光晕上，对比度会被拖到 4.0 左右。所以另给一组不透明定值 `--accent-tint` / `--red-tint` / `--green-tint` / `--orange-tint`（浅色是系统色兑白、深色是系统色兑近黑，兑的比例按 ≥4.6 反解）；半透明的 `--accent-soft` 只留给投影、光晕和装饰渐变这些需要 alpha 的地方。

**背景光晕保持样张原浓度（控制室 2026-09-23 裁定，四家统一）。** 实施时曾把透明度缩到六成 / 八成以让文字档全部 ≥4.5，屋主明确审美优先、不为对比度把底压平，于是恢复原值：六个强调色文字档压「玻璃叠自家最亮光晕角」的合成底实测 4.18–4.40，**记录不断言**（plan 同样情况同样处理）。

**光晕不显示的坑（2026-09-23 验收时抓到）。** `body::before` 用 `z-index:-1` 画光晕时，**body 不能再带不透明背景**：一旦 html 与 body 都写了 `background`，body 的背景不再传给画布，而是画在 body 盒子上，绘制顺序在负 z-index 的伪元素之上，三团光晕会被整个盖掉，页面看起来只是平底——而离线算出来的对比度数字照样「成立」。底色只写在 `html` 上，body 透明。

**次级文字由 `rgba(60,60,67,.62)` 调到 `.73`（四家统一）。** 苹果的 secondaryLabel 原值压在同一合成底上只有 3.42:1，且在纯白上也只有 3.63:1；`.73` 后五套 ≥4.5，靛色那套 4.49，记录不断言。深色的 `rgba(235,235,245,.62)` 本来就有 5.3+，不动。

**主按钮是全站唯一的可读性例外。** 屋主拍板：主按钮和左上角品牌图标用同一个亮渐变 `linear-gradient(135deg, var(--accent), var(--accent-2))` 加白字，浅色深色一样，原话是「所有颜色的按钮色可以和页面左上角的颜色一样浅一点」。白字压在渐变两端的实测值：

**选项键位另开一档。** 做题页选项左边那个 29 px 圆形字母是 13 px 粗体单字，填充档压不住它（白字压 `#34C759` 只有 1.9:1），所以键位底一律用文字档那一级，前景用 `--on-strong`（浅色 `#fff`、深色 `#0B0C10`）跟着翻。

**长面板不加 `backdrop-filter`。** 磨砂只放在视口大小的表面（侧栏、卡片、分组列表、弹窗、更新条）；做题页 `.question-surface` 那种整页高的面板改用 `--glass-strong` 当底——岗岗 2026-09-22 实测过显卡纹理上限问题。

**降级探针必须同时测前缀形式。** 不支持 `backdrop-filter` 时换成更实的底，探针写成 `@supports not ((backdrop-filter: blur(1px)) or (-webkit-backdrop-filter: blur(1px)))`。v3.11.2 之前只测了不带前缀的形式，iOS Safari 18 以前只认 `-webkit-backdrop-filter`，于是探针在那些浏览器上恒真、兜底档恒命中，玻璃一直是一块 .9 的实心白。

**窄屏分两段，不在 JS 里判视口。** `renderNav()` 同时产出三份 DOM，靠 CSS 断点切换显示：`#main-nav`（≥901 px 是左侧栏，600–900 px 收成顶栏：品牌 + 八项横向可滚的导航 + 末尾「更多」）、`#mobile-nav`（≤600 px 的底部玻璃 tab bar，首页 / 专项练习 / 搜题 / 更多）、`#more-layer`（两个断点共用的「更多」面板，600–900 从顶栏下拉、≤600 从底部弹出）。面板里放浅 / 深 / 自动、六个强调色圆点和版本号；其余五个导航项只在 ≤600 px 显示——600–900 px 顶栏已经有全部八项，再列一遍会像 bug。

**≤600 px 的手机档（2026-09-23 追加，屋主手机上提的六条）。** 规则全部写在 `styles.css` 的 `@media (max-width: 600px)` 块里，600 px 以上逐像素不变；需要 DOM 配合的三处（页头品牌块、首页副标题长短两份、环形卡右侧那半句）在桌面上都是 `display: none`，不在 JS 里判视口。
- **不要顶栏。** 这一档 `.sidebar` 只剩「品牌 + 刷刷」一条 56 px 白带（导航在底部 tab bar、主题控件在「更多」面板），整条 `display: none`，`.view` 顶部内边距收到安全区 + 10 px。品牌图标改由 `pageTitle()` 放进每一页大标题前面（30 px、圆角 9，与侧栏那枚同一个图案文件、同一条回落链）；做题页、结算页没有页头，也就没有这枚图标。「更多」面板仍从底部往上长，只加一个 `max-height`（上沿最多到安全区下 8 px、放不下面板内滚动）——**不能**照样张直接写 `top`：`top` 与 `bottom` 同时给定时网格把每一行拉高，417×750 下面板从 414 px 被撑到 672 px、每个导航项从 44 被拉到 73。
- **首页不堆信息。** 四张统计卡 2×2（去小字和图标、数字 20 px），今日复习、环形卡、最近学习各占一整行，最近学习仍排在环形卡后面（`order: 4`）；「随机20题」不放在手机首页（专项练习的一键选题里有），选择器只点名这一颗，并把只装着它的那个 `.header-actions` 一起收掉，否则纵向 flex 的 12 px 间距还在。首页副标题只留「题库：XXX」。
- **环形卡横排。** 圈 56 px、圈里只留数字，「今日已答 N · 每日目标…」挪到右边一行。原来 11 px 的「今日已答」四个字外接矩形虽在内圈的方框里，四角却在圆外（角到圆心 / 半径 = 1.039），这就是屋主说的「超出圆圈」；验收按「文字四角都在内圈的圆里」量，不按矩形。一天过千题时数字降到 14 px（18 px 的「1000」宽 46.5，内圈只有 45.9）。
- **搜题。** 两个下拉并排一行（两列网格，搜索框和按钮通栏，`select` 宽 100% + 省略号），手机上不展开解析。

**3D 槽位位置尺寸一个像素没动。** 首页 `data-fx-slot="home"` 仍在「今日复习」大卡右侧（≥1180 px 显示，`html.fx-ready .today-panel { padding-right: 300px }`），做题页 `.fx-slot-deck` 和结算页 `.fx-slot-summary` 的规则原样保留。为此首页那张大卡继续用 `.today-panel` 类名和 `position: relative; overflow: hidden`，只是从「深色渐变底白字」变成玻璃卡。

**首页「标记题专项」是新增入口。** 样张右列有它、原首页没有，用现成的 `data-action="practiceLibrary"` 并带上 `data-value="favorite"`；分发里加了一行守卫——带 `data-value` 时才改 `libraryFilter`，「错题与标记」页那颗按钮不带，行为一个字没变。样张漏掉的「模拟考试」保留，放在右列末尾（timer 图标、靛色）。

**3D 纸卡在深色下仍是白纸。** `PAPER` / `PAPER_SOFT` / `PAPER_EDGE` 保持 `#FFFFFF` / `#F6F7FB` / `#D9DEEA`（本来就偏冷，与玻璃卡一致），只把 `INK` 由 `#1F2333` 改成新的正文色 `#1C1C1E`。深色模式下纸依旧是白的——这是已知取舍：纸卡是「一叠真纸」的隐喻，做成深色就不是纸了，且三个场景的着色器、墨迹与红勾都按白纸调过。

**图标继续用 vendored lucide。** SPEC §5b 要求真 SVG 线条图标、禁止字符和 emoji 凑数；lucide 本来就是描边 SVG，只把 `createIcons` 的 `stroke-width` 由 1.8 统一成 1.9，导航 20 px、列表 18 px。列表行的图标底块按 SPEC：32 px、圆角 9、分类色实底 + 自上而下 22%→0 的白色高光 + 顶边内亮线 + 轻投影。品牌图标是 34 px 强调色渐变圆角方块 + 白色线条图案，图案本身改成**可替换的文件** `assets/brand/brand-icon.svg`（默认就是样张里那个「两张叠卡 + 勾」），屋主要换手绘 logo 直接覆盖它、或在同目录放 `brand-icon.png`；`index.html` 里那份内联 SVG 降级为回落，默认 `hidden`，由 `app.js` 的 `setUpBrandIcon()` 按 svg → png → 内联的顺序处理（在 `document` 的捕获阶段统一接 `error`，这样每次渲染新建的页头品牌块也覆盖得到；`brandIconSrc` 记住链走到了哪一档，之后渲染直接用那一档，不再重复失败；并兼顾脚本执行前就已失败的 `img`）。图标文件在方块里占 84%（屋主画稿四周已留白；内置回落 SVG 仍占 65%）、`object-fit: contain`，所以换成任何方形透明底白线图都不用改样式；换文件后必须递增 `sw.js` 缓存代次。`docker/nginx.conf` 没有路径白名单（只有 `try_files`），不需要改。列表图标那圈白线条压在分类色实底上是 1.55–5.65:1（非文本图形，WCAG 门槛 3:1，绿 / 橙 / 青三色低于 3:1）——这是 SPEC §5b 指定的做法，与主按钮同属审美优先，一并记在这里。

### 7.3 宽屏：等比放大、构图不变（v3.11.1 试错 → v3.11.2 定稿）

屋主 2026-09-23 在 2000px 宽的显示器上打开，内容在侧栏右边孤零零居中成一根约 900px 的窄柱、两边各空 450px。
**v3.11.1 的做法是错的**：把 `clamp()` 的上端往上抬（字只涨约 1.15 倍）、内容区放宽到 1560px（涨 1.36 倍）、
再在 ≥1600px 把「快速开始」拆成三列。屋主在 Windows 大屏上一看，说和 Mac 1440 的观感差太多——
问题正是「字涨得少、版面涨得多、还加了列」，结果整屏变密，不像同一个设计。

屋主有两台 Windows：台式 2040×1019 CSS px、DPR 1.25、没有显卡（WARP 软件渲染）；笔记本 2552×1274、DPR 1.5、RTX 4060。

**v3.11.2 改成整体等比缩放**，一条规则解决：

- 引入长度单位 `--u`，放在 `:root`：`--u: calc(clamp(1440px, 100vw, 2088px) / 1440)`。1440 及以下恰为 `1px`；
  往上与视口宽成正比（台式 2040 为 `1.4167px`）；2088（= 1440 × 1.45）起封顶 `1.45px`（笔记本 2552 触顶）。
  与 card / plan 用的是同一个公式。
- 样式表里**随构图一起放大**的 px 字面量全部写成 `calc(N * var(--u))`：字号、行高、字距、间距与内边距、
  圆角、图标尺寸、控件高度、列表行高、侧栏宽、投影偏移，以及三个 3D 槽位的尺寸。
- **不**乘 `--u`：媒体查询断点、1px 分隔线与玻璃亮线、`backdrop-filter` 的 blur、背景光晕的 vw 尺寸、焦点环的 2px。
  这几样放大只会变糙或变模糊，不属于「构图」。
- 随视口插值的那一组 token 在 `@media (min-width: 1441px)` 里换成「1440 处的值 × `--u`」：标题 34、h2 21.5、正文 15、
  间距 14.4、卡片内边距 17.3、侧栏 240、内容内边距 24。
- 「快速开始」的多列规则整条删掉，任何宽度下都是 1440 的构图。

实测（`Emulation.setDeviceMetricsOverride`）：台式 2040×1019@1.25 上 `--u` 1.4167、h1 48.17、侧栏 340；
笔记本 2552×1274@1.5 与 2560×1440 上 `--u` 1.45、h1 49.3、侧栏 348。

**为什么线性爬坡是错的。** 定稿前一版在 `@media (min-width: 1441px)` 里写
`--u: min(calc(1px + (100vw - 1440px) * 0.000401786), 1.45px)`——从 1440 的 1px 线性爬到 2560 的 1.45px。
它只在两个端点与等比重合，中间一律偏小：台式实际视口 2040 处只有 1.2411px，比等比的 1.4167 小约 14%，整屏小一圈，
这就是屋主反复说「和 Mac 差距大」的来源。等比公式在 2088 以内就是「把 1440 的版面整体放大 视口宽/1440 倍」，没有中间偏差。
1440 及以下 `clamp()` 把视口宽夹在 1440、除以 1440 正好是 1，`calc(N * var(--u))` 与 `N px` 数值完全相同，窄屏一个数都不变。

**封顶 1.45、放在 2088 而不是 2560。** 封顶是为了不让字号在超宽视口上无限放大；代价是超过 2088 之后构图逐渐变紧。
所以「缩到 1440 宽并排、相对大小肉眼无差别」这条验收**只在未触封顶的视口成立**：台式 2040@1.25（`--u` 1.417，未封顶）
是真的一致；笔记本 2552@1.5 触了 1.45 封顶，构图必然比 Mac 紧约 18%（2552 / 1440 = 1.77，而 `--u` 只到 1.45）——
这是主动选择的结果，不是达标。这个代价可以接受：笔记本是高 DPI（2552 CSS px × DPR 1.5，物理约 3840 宽），
1 CSS px 的物理尺寸比台式和 Mac 都小，所以 1.45 封顶下笔记本上正文的**物理大小**与 Mac 几乎相同——构图变紧换来
「一屏看到更多」，字并没有小到难读，这正是高分屏该有的行为。**屋主两台机器的观感会不一样，是预期不是 bug**：
台式未封顶、与 Mac 一致；笔记本封顶、内容更多更紧。在屋主反馈前不为「两台一样」去改封顶值。

**内容宽度是填满还是严格等比：选了填满，两台机器的差别不一样大。** `.view` 直接铺满侧栏右边的空间（不设上限、不居中）。
「严格等比」是把 1440 下的内容区（`.view` 盒宽 1440 − 244.8 ≈ 1195）乘 `--u`：

| 视口 | `--u` | 填满（视口 − 侧栏） | 严格等比（1195 × `--u`） | 差 |
| --- | --- | --- | --- | --- |
| 台式 2040×1019@1.25 | 1.4167 | 2040 − 340 = 1700 | 1693 | **7px** |
| 笔记本 2552×1274@1.5 | 1.45（封顶） | 2552 − 348 = 2204 | 1733 | 471px |

「只差 7px」**只对 2040 成立**：2088 以内两种做法几乎是一回事，台式机上并没有牺牲等比；「冲突时取填满」的取舍要到
2088 以上才拉开，笔记本上是真实的取舍（卡片比严格等比宽约 27%，字号、图标、间距与列数不变），裁定仍取填满。
`styles.css` 的 `.app-shell` 上方注释里写明了改回严格等比要换哪两行。

**侧栏加 `overflow-y: auto`，不许把唯一入口藏起来。** 侧栏底部那组（浅 / 深 / 自动、六色点、版本、进度）是切主题的
**唯一入口**。侧栏是 `height: 100vh` 的 sticky 列，内容跟着 `--u` 放大而视口高不跟：台式 2040×1019 下只剩约 24px 余量，
再挤一点底部那组就被裁掉，而且不留痕——用户只会以为「没有换色的地方」。加 `overflow-y: auto` 后，正常尺寸下
`scrollHeight == clientHeight`、不出滚动条、版面逐像素不变（实测 1440×900、2040×1019、2552×1274、2560×1440 溢出都是 0），
只在真挤时内部滚动。不用 `scrollbar-gutter: stable`：它会在所有尺寸预留一条，改动正常版面。

**竖向装不下：接受滚动，构图与 Mac 一致。** 台式 2040×1019 的屏比 Mac 1440×900 扁（宽高比 2.00 对 1.60），
内容高 ×1.417 而视口高只 ×1.13，首页需要滚动 312px（1440×900 是 42px、1440×720 是 222px）。明确否掉两种做法：
「竖向单独压缩（`--u-y`）」与「只压首页大卡的高度」——压竖向就是把构图改扁，而「构图和 Mac 一致」正是这轮要修的东西本身；
「首页要滚一点」在 Mac 的短窗口上本来就存在，不是大屏新引入的。

刷刷没有任何一处内容尺寸是按视口高算的，所以 card 那类『舞台按高算、卡跟着缩水』的问题在刷刷不存在。
实测做题页首屏（题干 + 选项 + 提交）在 1440×900 / 2040×1019 / 2560×1440 都一屏放得下（提交按钮所在的 footer 下沿 658 / 932 / 954）。

**边界上的小跳。** 1441 起用「1440 的设计值 × `--u`」，与 `clamp()` 在 1440 处的插值结果不完全相等，
所以正好拖过这一格时侧栏 244.8→240.2、内容内边距 28.8→24、标题 34.16→34.02 各跳一次；h2、间距、卡片内边距取的
就是 1440 处的实际插值（21.5 / 14.4 / 17.3），几乎不跳。

### 7.4 验收口径

- 门禁：`node scripts/release-check.mjs --check` 通过；`node --check` 覆盖 `theme.js` 等全部脚本；全仓不再出现 sky / mint / lilac / candy / mist / meadow 与「粉彩」。

### 8.1 硬约束：首页不许净增

### 8.2 只做一样：周总结

学习统计页加一个「按周回看」，照参考图的结构、按刷刷自己的口气重做：

- 一周一屏 8 格（手机 2×4、电脑 4×2 正好填满）：**汇总占一格**，不是横幅，加周一到周日七格。
- 每个日期格：左上星期与日号、右上当天合计题数，下面是当天碰过的题库色块，每块带该库当天的题数。
- 今天的日号套强调色圆底；未来的日子留空格子不填，一周形状完整。
- 左右箭头翻周，到本周时右箭头置灰。
- 汇总格只说事实，**不要感叹号堆叠的鼓励语**。

样张（手机 417×750、电脑 2040×1019，浅深各一张）已照此落地，见 CHANGELOG `[Unreleased]`。原先待拍板的三条，结论如下：

1. **题库短名。** 9 个内置题库在 `app.js` 的内置题库定义里给显式短名：`年检2026`、`年检2023`、`国内结算`、`票据融资`、`银承2024`、`反假货币`、`对公外汇`、`警示教育`、`外汇一级`；颜色与短名是同一份映射（定义里的 `short` / `chip`）。**不写进用户数据、不改存储、不需要迁移**——原设想的「给题库登记表加短名字段」不做。自建题库没有短名时按规则派生：去掉 `【】` 及其中文字，取前 4 个字；颜色按 id 的简单哈希落到这 9 色。
2. **一天超过 3 个题库。** 按当天题数从多到少显示前 3 块，第 4 行是一块中性色块「另 N 个题库 · M 题」。格子高度因此有上限，不截断文字。
3. **汇总格口径。** 大字「本周做题 N 题」；第一行「D 天有练习 · 正确率 X%」；第二行和上周比「比上周多 N 题 / 比上周少 N 题 / 和上周一样」，上周没有数据时第二行不显示。本周还没有记录时第一行写「本周还没有练习」。不显示时长（原因见 8.4）。

一并定下的：周一为一周的第一天，日期键与 `daily` 一样用本地年月日；学习统计页顶部分段控件「按周回看 / 累计统计」，默认按周回看、记住上次的选择，原有内容全部归「累计统计」；原「最近7天答题量」柱状图删除（只看当前题库、滚动 7 天，被按周回看完全覆盖）；未来的日子不计入汇总；首页不加任何东西（8.1）。

题库色：现有分类色只有 6 个，9 个库按苹果系统色补了紫 `#AF52DE`、褐 `#A2845E`、黄 `#FFCC00`，固定不随强调色变。浅深共 18 项对比度实测均 ≥4.5，其中三处比 §4 的现成值调了一档（深色蓝 `#6FB6FF`、深色靛 `#A5A3FF`、浅色粉 `#C20B3C`），依据是 §4 那句「按实际底再提亮一档」。

### 8.3 明确不做，以及为什么

1. **连续天数（streak）。** 屋主明说用不上。刷刷的激励模型就是「今日复习 + 每日目标」，不再加第二套。查证过：口径本身可行且不用新存储（各题库的 `daily` 按日期存，九个库并起来就能倒算历史），但日界只能用设备本地零点——`daily` 的键是本地年月日拼的字符串，里面没有时刻，「凌晨 N 点宽限」对历史生效不了。
2. **答题速度。** 屋主明说用不上。而且现有数据层**不支持**：没有任何地方记单题耗时，`record.lastAnsweredAt` 每次作答都覆盖，历史倒推不出来；要做得先给答题记录加时间戳、还要处理「挂着页面发呆」的上限，是笔不小的投入。
3. **番茄钟 / 计时逼迫。** 刷题缺的是题量和错题覆盖，不是坐得住。
4. **自习室、好友、排行。** 只有一个用户。
5. **分享周报。** 不会发给谁。

### 8.4 查证时顺带发现的：现有时长数字不可信

做 8.3 第 2 条的查证时发现，**`daily[日期].seconds` 与 `sessions[].duration` 现在就已经不可信**，与要不要做速度指标无关：

- 时长是结算时的 `(now − session.startedAt)/1000`，纯墙上时钟，**没有任何发呆上限**，挂着页面过夜全算进去。
- 连续刷题正常用不会结算：刷到题库最后一题会绕回第 1 题（`cycles += 1`），只有手动结束才记时长，那一场可能跨了好几天。
- 结算的时长按题数比例分摊到各题库，不是各库实际用时。

**因此周总结的汇总格不显示时长**，只显示题数、有练习的天数和正确率。以后要显示时长，必须先修这个口径。

### 8.5 另外两条现有行为（备份相关，容易踩）

- **合并备份对 `daily` 的三个数取大值，不相加。** 同一天在台式机做 30 题、笔记本做 20 题，合并后那天是 30 不是 50。周总结显示的题数会受这条影响。
- **日期按设备本地时间拼**，跨时区会错位。

## 九、练习入口的判据（2026-09-23 追加）

屋主原话：「连续刷题可以点击后回到原本刷题的地方吗，而不是从第一题开始」。查下来他看到「1/799」不是连续刷题坏了，而是换了题库（进度在旧的 1155 题库里）；真正静默丢进度的是另外两处。由此定下一条判据，以后加练习入口都照它办：

> **任何练习入口，要么默认续上，要么在点之前就写明会从头开始。**

### 9.1 三类入口各自怎么满足它

| 入口 | 位置存在哪 | 行为 |
| --- | --- | --- |
| 连续刷题 `startBrush` | `state.brush.index` | 默认续上。首页那一行右侧胶囊写「当前题号 / 总数」。这条本来就对，不要动。 |
| 自动看题 `startReviewSession` | `state.review = { index, signature, lastAt }` | 集合与上次相同就默认续上并提示「接着上次看到的第N题继续」；集合变了从第 1 题开始并提示「题目范围和上次不一样」。首页那一行右侧胶囊同样写题号，没有记录时不显示。 |
| 其余全部（专项练习、随机20题、今日复习、错题 / 不会 / 标记题专项、按题型练习、模拟考试、单题练习、本次错题重练） `startSession` | 只有 `activeSession`，没有第二处 | 没有「续上」可言，所以走「写明」：覆盖前若存在「答过题、还没结算」的会话，用一句 `confirm` 说清会丢什么（上次那一场的名字、做到第几题、已答多少题），取消就什么都不做。 |

### 9.2 为什么 `signature`，以及为什么不存整串题号

自动看题的题目集合不像连续刷题那样固定是整个题库：「专项练习」里选「自动看题」可以是任意子集，混合题库还会跨库。集合变了还按「第 N 题」续做，指的根本不是同一道题，所以必须能判「还是不是上次那一批」。

存整串题号能判，但整库 799 条约 8KB，而且**每翻一页都要写一遍**。所以存「条数 + 首尾题号 + 全部题号逐字算出的 32 位哈希」（如 `799:annual-2026-single-001:annual-2026-judge-808:hrrn0g`）：每个题号和它的位置都参与运算，与 `startBrush` 里逐个 id 比对一样对增、删、换序敏感，但长度固定。首页那个胶囊也用它对账——上次看的是子集时签名不同，胶囊就不显示，免得数字对不上。

### 9.3 三条容易踩的地方

- **位置抄在 `saveState()` 里，不在每个翻页函数里。** 自动翻页、上一题 / 下一题、按题号跳转、滑动翻页改完 `session.index` 之后都会调 `saveState()`，抄在那一处就不会漏掉哪条路径；`finishReview()` 会先把 `activeSession` 清掉，所以它自己先抄一次再清。
- **模拟考试做一半时没有判分记录。** 交卷才判分，半路只有已选答案，判「半截」时两处都要算，否则最该拦的模拟考试恰好拦不住。
- **首页不许为此新增元素。** 屋主说过「首页感觉内容太杂」，所以只用列表行右侧那个既有胶囊位（`.mode-badge`），标题在有位置时改成「继续自动看题」。
